## Context

Ver proposal.md - Why. Fase 5 ya estableció el DAL público (`findPublished`/`findGlobalPublished` en `src/lib/data/public-query.ts`, siempre `overrideAccess: false`), los view models (`src/lib/view-models/*.ts`), los componentes editoriales presentacionales (`src/components/editorial/*.tsx`) y el site shell dinámico (`(frontend)/layout.tsx`, `force-dynamic`). Ningún renderer de blocks existe todavía en el repo — ni para Home, ni para los Page Blocks ya definidos desde Fase 2 (`Hero`, `RichText`, `ImageText`, `Gallery`, `Video`, `CTA`, `FAQ`, `Banner` en `src/payload/blocks/page/`), que siguen sin consumidor en el frontend. Este change es la primera vez que se construye el patrón Payload Block → Resolver → View Model → Renderer → Section en este proyecto.

## Goals / Non-Goals

**Goals:**
- Fijar la ubicación de archivos y el flujo de tipos concreto para Home Global, blocks, resolver, renderer y sections.
- Fijar el contrato exacto (schema Payload + shape resuelto) de cada uno de los 8 bloques (`EditorialIntro` se aprobó durante revisión visual manual, ya con `dynamic-home-builder` en curso — ver D11).
- Fijar el mecanismo concreto de revalidación de contenido no publicado en relaciones manuales, verificado contra el comportamiento real de Payload instalado (no una suposición).
- Fijar cómo se comparte `Banner`/`BannerSection` entre Home y el futuro renderer de Pages sin acoplar este change a la implementación de Fase 7.
- Fijar cómo `seed:initial`/`seed:dev` extienden Home sin pisar configuración existente ni depender de contenido productivo falso.

**Non-Goals:**
- No diseñar `PageBlockRenderer` (Fase 7) — solo reubicar `Banner` a un lugar que ambos puedan importar.
- No diseñar Draft Mode ni rutas de preview (Fase 8) — solo el schema `versions: { drafts: true }`.
- No diseñar las rutas de Categoría/Artículo/Page genérica (Fase 7).

## Decisions

### D1. Ubicación de archivos sigue literalmente el árbol del Master Spec (§75)
`src/payload/blocks/home/*.ts` para el schema CMS y `src/components/sections/home/*.tsx` para la UI, en vez de mezclarlos con `blocks/page/`. El propio Master Spec (§59) trata "Payload Block" y "React Section" como conceptos distintos con ejemplos explícitos de ambos paths.

### D2. Resolver como capa propia, separada del DAL
`src/lib/home/resolve-home-blocks.ts` (nuevo) contiene `resolveHomeBlocks(rawLayout)`, con una función de resolución por tipo de bloque. El DAL (`getHome()`, `getPostsByCategory()`) solo obtiene datos crudos con `overrideAccess: false`; el resolver los normaliza. Alternativa descartada: normalizar dentro de `getHome()` mismo — mezclaría acceso a datos con lógica de negocio de resolución y dificultaría probar cada responsabilidad por separado.

### D3. Ubicación de las nuevas funciones del DAL
`getHome()` en `src/lib/data/home.ts` nuevo (mismo patrón de una función por archivo que `footer.ts`/`navigation.ts`/`settings.ts`). `getPostsByCategory({ categoryId, limit })` se añade a `src/lib/data/posts.ts` ya existente, junto a `getLatestPosts()`, porque ambas son queries de `Posts`.

### D4. `Banner` se reubica a un módulo compartido, no se duplica
El schema Payload se mueve a `src/payload/blocks/shared/Banner.ts` (mismo objeto `Block`, mismo `slug: 'banner'`), importado tanto por `Pages.layout` como por `Home.layout`. La sección se implementa una sola vez en `src/components/sections/banner-section.tsx` (fuera de `sections/home/` y de `sections/pages/`, precisamente porque es compartida por ambos). No se toca el comportamiento de renderizado de `Pages` — sigue sin tener renderer hasta Fase 7; Fase 7 solo importa `BannerSection` en vez de rediseñarla. Alternativa descartada: duplicar el schema en `blocks/home/Banner.ts` — viola la Decisión F ya confirmada y arriesga que ambos schemas diverjan con el tiempo.

### D5. Revalidación de relaciones manuales: verificado contra Payload instalado, no asumido
Se inspeccionó `node_modules/payload/dist/fields/hooks/afterRead/relationshipPopulationPromise.js` (v3.87.1). Cuando una relación no puede poblarse — incluyendo por fallo de control de acceso, como un Post en Draft bajo `overrideAccess: false` — Payload cae de vuelta al ID crudo (`relationshipValue = id`, con el comentario propio de Payload "ids are visible regardless of access controls"), nunca a `null` ni a un objeto parcial. Esto es exactamente el mismo caso que los view models de Fase 5 ya manejan: `mapPostToArticleCardData` ya trata `typeof primaryCategory === 'number'` como "no se pudo mapear". `resolveHomeBlocks` SHALL aplicar el mismo criterio a cada relación manual (`HeroNews.mainPost`/`secondaryPosts`, `FeaturedPosts.posts`, `VideoFeature.post`): si la relación llega como número en vez de objeto poblado, se trata como ausente. No se necesita una re-query adicional por bloque — el propio `getHome()` con `depth` suficiente y `overrideAccess: false` ya produce el resultado seguro.

### D6. `HomeBlockRenderer` como un switch exhaustivo, no un registry
Un único `switch` sobre el `type` resuelto de cada bloque, con `default` que hace `console.warn` y devuelve `null`, apoyado en el chequeo de exhaustividad de TypeScript (`never` en el `default`) para que agregar un bloque futuro sin su `case` correspondiente sea un error de compilación. Alternativa descartada: un registry tipo Map/plugin — innecesario para un conjunto fijo y pequeño (7) de bloques V1 definido por el Master Spec; añade indirección sin beneficio real.

### D7. Un único H1 en Home mediante un H1 fuera de las Sections, no dentro del bloque Hero
La página de Home renderiza un `<h1 className="sr-only">{siteName}</h1>` propio (mismo idioma visual que el skip-link `sr-only` ya usado en `(frontend)/layout.tsx`), independiente del layout configurado. `HeroNewsSection` — y cualquier otra Section — nunca renderiza un `<h1>`; su titular usa `<h2>` (o el nivel que corresponda) con la escala tipográfica visual de H1 si el diseño lo requiere. Esto garantiza un único H1 sin importar si el Admin mueve, quita o no configura `HeroNews`. Alternativa descartada: que el primer bloque resuelto "sea" el H1 dinámicamente — frágil (la identidad del H1 cambia o desaparece según el reordenamiento del Admin) y acopla `HomeBlockRenderer` a la semántica de un bloque específico, contrario al principio de §61 de que un Section no debería depender de detalles de otro.

### D8. Baseline de `seed:initial`: un único bloque `CategoryExplorer`
De los 7 bloques V1, `CategoryExplorer` es el único cuyo contenido (`categories hasMany`) no depende de que existan Posts reales. `seed:initial` configura `Home.layout` con un único `CategoryExplorerBlock` referenciando las `INITIAL_CATEGORIES` que el mismo script ya crea, solo si `Home.layout` está vacío (para no pisar una configuración ya guardada por un Admin). Alternativa descartada: dejar `Home.layout` vacío en `seed:initial` — técnicamente válido (`home-block-renderer` degrada bien), pero no demuestra que el pipeline CMS-driven funciona de inmediato en una instalación nueva, que es justamente lo que el Master Spec pide al listar "Home base" como parte de `seed:initial`.

### D9. `seed:dev` añade bloques representativos por anexión, no por reemplazo
`seed:dev` no reemplaza `Home.layout`; le **anexa** un bloque `LatestPosts` y un bloque `FeaturedPosts` (seleccionando manualmente el Post publicado que el propio `seed:dev` crea), usando un `title` fijo y reconocible como clave de idempotencia (igual que el resto de `seed:dev` ya usa `slug`/`alt` para su propio criterio de "ya existe"). Si `seed:dev` se ejecuta de nuevo y encuentra un bloque con ese `title` ya presente, no lo duplica. Esto es intencional: como `seed:initial` siempre deja al menos el bloque `CategoryExplorer` de la Decisión D8, un chequeo de "layout vacío" nunca se cumpliría en el flujo normal (`seed:initial` primero, `seed:dev` después).

### D10. Validación de proveedor de video externo: módulo nuevo, sin acoplar a Article
`src/lib/editorial/video-provider.ts` (mismo nivel que `category-theme.ts`) expone `resolveExternalVideoUrl(url): { provider: 'youtube' | 'vimeo'; embedId: string } | undefined`, con un allowlist de hostnames por proveedor (incluyendo variantes como `youtu.be`) y extracción de ID por proveedor. No reutiliza `src/payload/blocks/article/VideoBlock.ts` porque ese archivo es únicamente schema de Payload (un `select` de proveedor elegido por el editor) — no existe hoy ningún parser de URL que reutilizar; ambos bloques comparten la filosofía de "proveedor controlado", no código.

### D11. `EditorialIntro`: dos capas de Media independientes, sin nueva query ni nuevo DAL
`backgroundImage`/`foregroundImage` se resuelven con el mismo `mapMediaToMediaData()` de Fase 5 ya usado por todos los demás bloques — no se necesita una función de DAL nueva ni una consulta adicional, porque ambos son relaciones directas de `Home.layout[]` ya pobladas por `getHome({ depth: 2 })`. `EditorialIntroSection` compone las dos imágenes con CSS (fondo a ancho completo del `<section>`, primer plano posicionado encima vía posicionamiento absoluto/superposición, igual patrón `position:relative` + capas que ya usa `HeroNewsSection`/`.texture-newspaper-pattern` para su textura decorativa) — sin introducir una librería de composición de imágenes ni un segundo `ResponsiveMedia`. El titular en dos colores (`headlinePrimary` en tinta, `headlineAccent` en rojo de marca) se resuelve como dos strings planos; el componente decide el color por prop, no por HTML/CSS proveniente del CMS. Alternativa descartada: modelar el fondo como campos separados (mapa, collage) — explícitamente rechazado por el requisito aprobado; el Admin provee una sola composición preparada, el componente no construye la composición de fondo a partir de piezas.

### D12. CTA de `HeroNews`/`Banner`/`EditorialIntro` unificado sobre `linkFields`, no un par de campos de texto plano
Los tres bloques que tienen un enlace de llamada a la acción (`HeroNews.ctaLabel`/`ctaLink`, `Banner.linkLabel`/`linkURL`, `EditorialIntro.ctaLabel`/`ctaLink`) pasan a usar un campo `group` (`cta` en `HeroNews`/`EditorialIntro`, `link` en `Banner`) con `fields: linkFields` — el mismo modelo ya usado por `Navigation.items`/`Footer.columns[].links`. El Admin obtiene el mismo selector `Category | Page | External` que ya tiene en Navigation/Footer, en vez de un campo de texto libre. El resolver de cada bloque usa `resolveLink()` directamente sobre ese grupo, igual que ya hacen `resolveNavItems()`/`resolveLinks()`.

Esto reemplaza una decisión previa de esta misma fase: un primer intento (`resolveFlatLink()`, agregado para resolver un bug real — `EditorialIntro.ctaLink: '/'` desaparecía el bloque completo porque el validador solo aceptaba URLs externas absolutas) quedó superado por esta unificación, ya que el selector de tipo hace innecesario adivinar si una URL de texto libre es interna o externa. `resolveFlatLink()` se elimina de `resolve-link.ts` — no queda ningún llamador.

Alternativa descartada: mantener el campo de texto plano y solo mejorar la heurística de `resolveFlatLink()` (aceptar rutas relativas) — rechazada porque no resuelve el problema real señalado por el usuario (no poder enlazar a una Category/Page existente sin escribir su URL a mano) y perpetúa una inconsistencia con Navigation/Footer, que sí ofrecen ese selector.

### D13. Migración del cambio de CTA dividida en dos pasos (aditivo, luego remoción)
Quitar `ctaLabel`/`ctaLink` (o `linkLabel`/`linkURL`) y agregar el grupo `cta`/`link` en el mismo `migrate:create` produce una columna nueva (`cta_type`/`link_type`) y una columna removida (`cta_link`/`link_u_r_l`) en la misma tabla — Drizzle no puede distinguir eso de un renombre y pide confirmación interactiva (`+ create column` vs `~ rename column`), un prompt que necesita una TTY que este entorno no tiene. Se dividió en dos migraciones: primero `cta_link_fields_add` (solo agrega columnas nuevas, dejando temporalmente los campos viejos en el código), después `cta_link_fields_remove_old` (solo remueve las columnas viejas, ya sin ningún campo nuevo compitiendo en el mismo diff). Cada paso, al no tener una adición y una remoción simultánea en la misma tabla, generó sin ninguna ambigüedad. Aplicado a la base de desarrollo push-managed en los mismos dos pasos (dos reinicios del contenedor), con el desarrollador aprobando manualmente desde una terminal interactiva la advertencia de pérdida de datos del segundo paso (columnas viejas con historial de versiones). El dato real existente (`EditorialIntro.ctaLabel`/`ctaLink`) se copió a las columnas nuevas (`cta_label`/`cta_url`, con `cta_type: 'external'`) antes de remover las viejas — ver Riesgos.

## Risks / Trade-offs

- [El H1 accesible-pero-oculto (D7) separa el H1 semántico del titular visualmente más prominente] → Mitigación: QA visual manual confirmando que el Hero sigue leyéndose como el elemento principal de la página aunque semánticamente sea H2.
- [Compartir `Banner`/`BannerSection` (D4) crea una dependencia implícita entre este change y el futuro `PageBlockRenderer` de Fase 7] → Mitigación: documentar la reubicación en `docs/FRONTEND-ARCHITECTURE.md` para que Fase 7 solo necesite importar, no rediseñar; no se modifica ningún comportamiento observable de `Pages` en este change.
- [El comportamiento de fallback de Payload verificado en D5 es un detalle interno no documentado públicamente por Payload] → Mitigación: el mismo criterio de "verificar contra el código instalado" ya se aplica en `public-query.ts` para el select-mode; si una futura actualización de Payload cambia este comportamiento, el chequeo `typeof === number` en los mappers seguiría siendo la defensa correcta con cualquier valor no-objeto que Payload decida devolver.
- [El allowlist de hostnames de YouTube/Vimeo (D10) puede ser demasiado estricto y rechazar variantes legítimas] → Mitigación: enumerar explícitamente las variantes conocidas (`youtube.com`, `youtu.be`, `player.vimeo.com`, `vimeo.com`) en tasks.md y cubrirlas con casos de prueba antes de considerar el bloque terminado.
- [`seed:dev` anexando bloques a un Global singleton (D9) depende de un `title` fijo como clave de idempotencia, más frágil que una clave `slug` real] → Mitigación: documentar el `title` exacto usado como constante exportada, para que no diverja entre el chequeo de idempotencia y el bloque creado.
- [`EditorialIntro` (D11) se aprobó a partir de una referencia visual estática (`docs/references/home-reference.jpeg`), no de un mockup interactivo por breakpoint — la composición exacta de `foregroundImage` superpuesto sobre `backgroundImage` en mobile es una interpretación, no una especificación pixel-perfect] → Mitigación: QA visual manual obligatoria en los anchos definidos por tasks.md antes de dar por completo el bloque; no se marca la verificación visual como hecha sin confirmación humana real.
- [D12: `linkFields.label`/`linkFields.type` están marcados `required: true` en el array compartido; usarlo dentro de un grupo `cta`/`link` opcional en `HeroNews`/`Banner` podría forzar a Payload a exigir esos subcampos incluso cuando el Admin no quiere configurar ningún CTA] → **Confirmado (no solo hipotético): sí ocurría.** Guardar el `Home` real de desarrollo con un `HeroNews.cta` vacío falló con "This field is required" en `cta.label`/`cta.type` — el `HeroNews` real ya configurado antes de este cambio quedó en ese estado y no podía volver a guardarse (la lectura pública no se vio afectada; Payload solo revalida en escritura). Corregido con `optionalLinkFields` en `link-fields.ts` (el mismo array de `linkFields`, con `label`/`type` reescritos a `required: false` vía `.map()` — un solo modelo, sin duplicar campos/opciones) usado por `HeroNews`/`Banner`; `EditorialIntro` sigue con `linkFields` sin cambios porque su CTA es requerido por diseño. `resolveLink()`/`LinkLike` se extendieron para aceptar `label`/`type`/el item completo como opcionales. Verificado guardando el `Home` real de nuevo sin error tras el fix.
- [El `EditorialIntro` real de desarrollo tenía `ctaLink: "/"` (heredado de antes de D12), migrado a `cta: { type: 'external', url: '/' }` para no perder el dato, pero `"/"` no es una URL externa válida bajo `linkFields` (`isSafeExternalUrl` exige `http(s)://`) y no existe un tipo de link para "la portada" en el modelo Category/Page/External] → El bloque se oculta hasta que el Admin lo reconfigure con un destino real (`type: 'page'`/`'category'` a un documento existente, o una URL externa completa) — no se reconfiguró automáticamente porque es una decisión editorial, no técnica.

## Migration Plan

- Registrar `Home` en `payload.config.ts`, correr `pnpm migrate:create` contra la base de datos de desarrollo, revisar el SQL generado antes de commitear.
- Commitear el par `.json`/`.ts` de la migración en `src/payload/migrations/`, siguiendo el mismo patrón que las dos migraciones ya existentes.
- Regenerar `src/payload-types.ts` con `pnpm generate:types` y commitear el resultado.
- Sin estrategia de rollback especial: el Global es nuevo, sin datos productivos previos que preservar; `pnpm payload migrate:down` estándar basta si se necesita revertir en desarrollo.
