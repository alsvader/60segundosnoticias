# Project AI Skills Registry

## Purpose

This file is the human-readable registry and routing policy for AI skills intentionally adopted by the 60 Segundos repository. The machine-readable installed roster is `skills-lock.json` at the repository root.

`skills-lock.json` is the canonical record for upstream source, skill path and computed content hash. Do not hand-edit its hashes. Regenerate/update it through the adopted skills installer when skills change.

The Master Spec and active OpenSpec change always outrank skill guidance. Skills provide procedural guidance only; they must not redefine product requirements or architecture.

## Adopted project skills

The current lock contains **16 project skills**. They should be installed project-scoped rather than globally unless the project owner explicitly changes that policy. The current skills roster is the one captured in `skills-lock.json`.

### Routing policy

Do **not** load every skill for every task. Select only the skills that materially apply to the active OpenSpec change or verification step. This prevents duplicated guidance, conflicting heuristics and unnecessary context usage.

Use the following precedence for overlapping guidance:

1. Master Spec / active OpenSpec change.
2. Existing project design-system and architecture constraints.
3. Most task-specific skill.
4. Broad audit/review skill.

In particular:

- For UI implementation, prefer `tailwind-design-system` for token/component mechanics; use `design-taste-frontend` and `ui-ux-pro-max` selectively for polish/UX review.
- For web quality, invoke focused skills (`accessibility`, `core-web-vitals`, `performance`, `seo`) during relevant work; reserve `web-quality-audit` for broad review gates.
- Use PostgreSQL skills only when the active change touches database/schema/query concerns.
- Use `multi-stage-dockerfile` only for Dockerfile/container work, `playwright-best-practices` for Playwright work, and `git-commit` at commit preparation time.

## Installation order inside Phase -1

1. Install/verify the local runtimes and CLIs.
2. Initialize OpenSpec for the adopted agents.
3. Install the project skills in this registry.
4. Confirm `skills-lock.json` matches the intended roster.
5. Install Graphify project integrations for Claude/Codex.
6. Review `.graphifyignore` and agent instructions.
7. Build the first Graphify graph.
8. Validate Phase -1 and create the baseline tooling commit.

Installing skills before the first Graphify build does not mean Graphify should index the generated skill payloads. Agent skill implementation directories remain excluded by `.graphifyignore`; the graph should focus on the product repository, documentation and OpenSpec artifacts.

## Update rule

Whenever a skill is installed, removed or upgraded:

1. use the adopted skills CLI rather than editing installed payloads manually;
2. update/regenerate `skills-lock.json`;
3. review the source/path/hash diff;
4. update this human-readable routing registry if the roster or intended usage changed;
5. verify generated project-scoped files contain no secrets or machine-specific paths;
6. confirm the skill does not conflict with `AGENTS.md`, the Master Spec or the active OpenSpec change;
7. refresh Graphify only if intentionally graphed repository content changed.

## Security note

Third-party skills are executable/procedural agent guidance. Review upstream changes before accepting updates. A matching lock hash establishes reproducibility of the selected content; it is not a security guarantee.
