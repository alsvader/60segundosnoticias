# AI / SDD Workflow — 60 Segundos Noticias

## Purpose

This repository uses a layered development workflow so AI agents can work with a large project without repeatedly scanning the entire codebase or turning one giant document into an unmanageable implementation prompt.

The layers have different responsibilities:

```text
docs/60-segundos-spec.md
        │
        │ target state / product contract
        ▼
Graphify
        │
        │ current repository structure and impact map
        ▼
OpenSpec change
        │
        │ exact scope being designed/implemented now
        ▼
Implementation
        │
        ▼
Graphify update
        │
        ▼
OpenSpec verify + AC review
        │
        ▼
OpenSpec archive
        │
        ▼
openspec/specs/ = implemented behavior
```

## Responsibilities

### Master Specification

`docs/60-segundos-spec.md` is the canonical target definition for V1. It owns product behavior, CMS architecture, frontend architecture, design system, infrastructure constraints, implementation phases and acceptance criteria.

It answers: **What must 60 Segundos become?**

### OpenSpec

OpenSpec governs product changes from Phase 0 onward. An active change contains the proposal, delta specs, design and tasks for one coherent implementation slice.

It answers: **What are we changing now, why, and how will we prove it?**

Do not turn the entire Master Spec into one giant OpenSpec change. Create changes incrementally by implementation phase or by a smaller coherent slice when a phase is too large.

### Graphify

Graphify represents the current structure of the repository as a knowledge graph. Agents should query it before broad exploration, then inspect only the relevant source files needed to confirm the graph and implement the change.

It answers: **How is the repository currently connected, and what could this change affect?**

The graph is a snapshot, not an authority. Source code wins when the graph is stale or ambiguous.

### Project skills

Project-scoped skills provide specialized procedural guidance for supported tools or domains. Their human-readable routing registry is maintained in `docs/AI-SKILLS.md`, while `skills-lock.json` is the machine-readable locked roster (source/path/hash). Skills may improve execution, but they do not override the Master Spec or an active OpenSpec change. Do not load the complete skill roster for every task; select the smallest relevant set.

## Phase -1 — Repository AI bootstrap

Phase -1 configures the repository tooling itself. It is intentionally outside the normal OpenSpec product-change lifecycle because OpenSpec is one of the tools being bootstrapped.

Phase -1 is complete when:

- repository instructions exist;
- OpenSpec is initialized and configured;
- selected project skills are registered and documented;
- Graphify is installed project-scoped for the adopted agents;
- `.graphifyignore` is configured;
- a first graph can be built and queried;
- the shared Graphify output is ready to be committed;
- no secrets or machine-specific credentials are committed;
- a baseline tooling commit exists before product implementation.

## New clone onboarding

### 1. Clone and inspect

```bash
git clone <repository-url>
cd <repository>
./scripts/ai/check-environment.sh
```

The script only checks prerequisites; it does not install global software automatically.

### 2. Install OpenSpec CLI

Install OpenSpec using the installation method recommended by the OpenSpec version adopted by the project, then verify:

```bash
openspec --version
```

Run `openspec init` when initializing integrations for the first time. Select the coding agents the team actually uses. If the repository already contains project-scoped generated integrations, use `openspec update` when the installed OpenSpec version requires refreshing them rather than recreating project decisions manually.

The project-owned configuration is `openspec/config.yaml`. Do not replace it with a generic default.

For this project, prefer an OpenSpec workflow profile that includes `verify`. The exact generated command syntax can differ by agent/version, so use the commands generated by the installed OpenSpec release.

### 3. Install additional project skills

Install only the skills registered in `docs/AI-SKILLS.md` and locked in `skills-lock.json`. Project scope is the default for this repository. The skills CLI can be run via `npx`; use the exact per-skill commands documented in `docs/AI-SKILLS.md`.

After adding/removing/upgrading a skill, regenerate/update `skills-lock.json` and update `docs/AI-SKILLS.md` if the routing policy or roster changed.

### 4. Install Graphify

Graphify currently ships as the `graphifyy` Python package and the installed command is `graphify`. A recommended isolated installation is:

```bash
uv tool install graphifyy
graphify --version
```

Register it project-scoped for the agents you use:

```bash
graphify claude install --project
graphify codex install --project
```

Codex invokes the skill with `$graphify`; Claude Code uses `/graphify`. Follow the installed version's output if command details change.

Any Codex user-level settings required by the current Graphify release belong in the developer's local Codex configuration and must not be committed as personal configuration.

### 5. Build or refresh the graph

Inside the supported assistant:

```text
/graphify .
```

Codex equivalent:

```text
$graphify .
```

Incremental refresh:

```text
/graphify . --update
```

Graphify writes the shared graph under `graphify-out/`. The directory is intended to be committed so a teammate who clones the repository starts with a usable map. The graph must still be refreshed when the source has changed materially.

Optionally install Graphify's Git hook after the repository is initialized:

```bash
graphify hook install
```

## Workflow for each product change

### A. Explore

1. Read `AGENTS.md`.
2. Query Graphify for the subsystem, dependencies and likely blast radius.
3. Inspect only the relevant current source files.
4. Read the relevant Master Spec sections and `AC-*` criteria.
5. Use OpenSpec explore when useful to investigate without committing to a change design.

### B. Create the OpenSpec change

Create one coherent change. For the initial roadmap, prefer the Master Spec implementation phases as boundaries unless a phase is too broad and benefits from smaller independent changes.

The change artifacts should:

- identify the exact Master Spec phase/sections involved;
- derive requirements from the Master Spec rather than inventing parallel requirements;
- preserve relevant `AC-*` IDs for traceability;
- state what is explicitly out of scope;
- use Graphify findings to describe current integration points;
- keep implementation mechanisms in `design.md`, not behavioral specs.

### C. Human review

Before apply, review proposal, specs, design and tasks. Reject scope creep, duplicate architecture, unnecessary dependencies and requirements that contradict the Master Spec.

### D. Apply

Implement only the active change. Use Graphify to narrow source inspection and confirm actual files before editing.

### E. Validate

Run the checks defined in `tasks.md`, such as typecheck, lint, focused tests, integration/E2E tests and production build when applicable.

### F. Refresh Graphify

Refresh the graph after meaningful code/documentation changes when the current graph no longer represents the working tree.

### G. Verify

Run OpenSpec verify. In addition, report all Master Spec acceptance criteria referenced by the change as:

- `PASS`
- `FAIL`
- `NOT TESTED`
- `NOT APPLICABLE`

Do not consider a required change ready to archive while required criteria are `FAIL` or `NOT TESTED`.

### H. Archive

Archive only after implementation and verification are complete. Archived delta specs should update the OpenSpec current-state specs according to the OpenSpec workflow.

## Rules for keeping context small

- Do not reread the entire repository when Graphify can identify the relevant area.
- Do not paste the entire Master Spec into OpenSpec artifacts.
- Do not duplicate repository-wide rules into every skill.
- Prefer links/paths to canonical documents plus the exact relevant requirements.
- Inspect source code before editing even when Graphify provides a likely answer.
- Refresh Graphify when source changes make the existing graph stale.

## Tooling boundary

OpenSpec, Graphify, Claude Code, Codex and project skills are development tooling. The application must build and run without them. Production containers must not install or depend on these tools.
